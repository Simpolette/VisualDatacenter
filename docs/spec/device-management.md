# Device Management Specification

## 1. Description
Provides functional capabilities to install hardware devices into U-slots inside a server rack, update their parameters, and uninstall them. Slot allocation is strictly validated on the backend to prevent multi-device physical overlaps.

---

## 2. Main Flow
1.  **Open Inspector**: The user selects a rack in the 3D room canvas to open the 2D rack inspector sidebar.
2.  **Add Device**: The user clicks the "Add Device" button.
3.  **Form Entry**: The user selects a device template from the dropdown, enters the device name (auto-generated by default), chooses the starting U-slot position, and selects the mounting face (`FRONT` or `REAR`).
4.  **Submission**: The user submits the form.
5.  **API Execution**: The frontend POSTs an `InstallDeviceDTO` to `POST /api/v1/racks/:rackId/devices`.
6.  **Server Validation**: The backend checks:
    *   If the device fits within the rack's unit height.
    *   If any existing device overlaps the target U-slot range on the same face.
7.  **Persist & Refresh**: The backend saves the `Device` entity. The frontend reloads the rack details, collapsing the form and drawing the new device faceplate in the 2D slot grid and the 3D X-Ray device stack.

---

## 3. Access Control
*   **Authorization Level**: Single-user sandbox model.
*   **Policy**: No authentication or role-based restrictions. Full privileges are granted to all API client requests.

---

## 4. Data Model

### InstallDeviceDTO / UpdateDeviceDTO
*   `deviceTypeId` (Long, Required)
*   `name` (String, Required)
*   `startU` (Integer, Required - must be >= 1)
*   `face` (Enum [FRONT, REAR], Optional - defaults to FRONT)
*   `status` (Enum [ACTIVE, MAINTENANCE, OFFLINE], Optional - defaults to ACTIVE)

### DeviceDetailDTO
*   `id` (Long)
*   `rackId` (Long)
*   `deviceType` (DeviceType object)
*   `name` (String)
*   `startU` (Integer)
*   `face` (Enum [FRONT, REAR])
*   `status` (Enum [ACTIVE, MAINTENANCE, OFFLINE])
*   `createdAt` (Timestamp)
*   `updatedAt` (Timestamp)

---

## 5. Error Scenarios

| Trigger | Condition | Expected System Behavior |
| :--- | :--- | :--- |
| **Device Installation / Move** | Selected slots overlap with an existing device on the *same* face | Backend aborts transaction and returns `HTTP 409 Conflict` with overlapping slot numbers. Frontend displays the collision error message in the form. |
| **Device Installation / Move** | The device's height causes it to exceed the top unit of the rack | Backend returns `HTTP 400 Bad Request`. Frontend alerts the user that the device exceeds rack boundaries. |
| **Device Installation** | `startU < 1` | System validation fails. Returns `HTTP 400 Bad Request`. |
| **Device Installation** | Specified `deviceTypeId` does not exist | Returns `HTTP 404 Not Found`. |

---

## 6. Constraints
*   **Unit Bounds**: $1 \le \text{startU} \le \text{startU} + \text{heightU} - 1 \le \text{rack.totalUnits}$.

---

## 7. Acceptance Criteria
*   The 2D sidebar grid displays slots numbered vertically from bottom (1) to top (42 or 44).
*   Devices occupying slots are visually rendered in the grid, spanning exactly their U-height.
*   Selecting a device type auto-populates the name field using the format `{deviceTypeName} #{nextIndex}`.
*   Front-panel images are rendered on device cards; fallback slate cards render simulated screws.
*   3D rack scene dynamically binds `frontImagePath` to front mesh face and `rearImagePath` to rear mesh face.
*   Clicking the delete button displays an inline confirmation message before deleting.
*   Overlapping slot placements on the same face are rejected with an HTTP 409 error.
